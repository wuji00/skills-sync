# Vibe Coding 稳定性审计

判断 AI 生成的产品稳不稳，标准只有一个：**它坏掉的时候，你隔多久能知道**。别问它能不能跑起来。测试全绿、演示顺利、自己觉得挺稳，都不算证据。

贯穿概念：**出声**。AI 代码最危险的失败形态是"安静地犯错"——返回 200、日志干净、然后输出垃圾。审计的目标就是让它坏的时候当场出声。

## 第 1 步：分档，定验收标准

判断"坏了谁会先知道"：只有自己 → 第一档（跑通即达标）；同事 → 第二档（内部工具标准）；陌生人 → 第三档（验收与手写代码完全一致，一格不降）。

**完成标准：** 明确档位。第三档（对外/收钱/存用户数据）走完以下所有步骤；第一二档跳到第 5 步。

## 第 2 步：四层验证栈逐层检查

1. **确定性检查**（成本最低，别关掉它）：类型检查、lint、密钥扫描、依赖审计、SAST
2. **语义验证**（贵，只覆盖核心路径）：变异测试（JS/TS→Stryker、Java→PIT、Python→mutmut）+ 契约测试
   - 关键路径变异分数 < 70% 当没测过，普通功能 50% 是底线
   - 覆盖率不算证据：行覆盖 100% + 变异分数 4% = 测试在旁边看着，没在验证
   - AI 生成的测试是"自己给自己出考卷"：承重功能（坏了用户会骂街的）断言必须人工手写
3. **可观测性**（性价比最高），必须双线配齐：
   - 崩溃线（进程级死法）：Sentry / Crashlytics / 腾讯 Bugly / 友盟 U-APM / 火山 APMPlus
   - 事件线（业务级死法）：行为埋点、漏斗——AI 代码典型失败是用户走不到下一步
4. **渐进发布**（兜底）：feature flag、金丝雀、分阶段放量。回滚能力本身就是稳定性指标

**完成标准：** 每层逐项回答"有/没有/是否覆盖核心路径"，缺层明确指出。

## 第 3 步：LLM 功能三层兜底（仅当产品含 LLM 驱动功能）

单测对 LLM 功能失效（同输入不同输出、且都可能是对的），三层评估：
1. **完整性检查**（最外层，毫秒级）：JSON 可解析、分类在预期标签集、结果条数非 0、引用 URL 真实存在
2. **冻结 golden set**（中间）：10–50 个真实用户输入，预期行为写成文档，改 prompt/换模型/升级依赖整套重跑。30 个真实输入 > 整个公开排行榜（公开基准会泄漏进训练数据，且不测你的任务）
3. **LLM-as-judge**（最里层）：⚠️ 防同族模型偏差——评委与生成用**不同厂商**的模型，定期人工抽样校准，拿人工分数当锚

**完成标准：** 三层各自说明覆盖情况，且确认线上失败案例有回流进 golden set 的机制。

## 第 4 步：翻车根因三类排查

2025–2026 公开 vibe coding 事故根因高度集中，且都不属于"功能是否正确"，常规测试测不到：
1. **权限与密钥的默认配置**：Firebase 存储桶权限、Supabase RLS 是否启用、key 是否进了前端（实测 11% 的应用前端暴露 Supabase 凭证）
2. **AI 对破坏性操作没有边界约束**：删库/覆盖/批量操作的确认机制、代码冻结指令是否有效（Replit 删生产库事故）
3. **资源消耗没有上限**：agent 死循环、嵌套循环代替 SQL join、无上限的 token/账单

**完成标准：** 三类逐项排查并给出结论。

## 第 5 步：输出审计结论

按「**能观测 / 能度量 / 能回滚**」三件事是否凑齐下结论——凑齐了才算能用，不管代码谁写的。

- 每层：有/没有、缺什么、最小补齐动作（30 行内能解决的别拖成大工程）
- 没有可对照基线的"感觉挺稳"是自我安慰：用控制变量法（同一需求人写 vs AI 写跑同一套变异测试；同一 prompt 换模型跑 golden set）验证
