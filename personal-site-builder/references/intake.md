# 资料采集与内容模型

## 最小启动资料

凑齐这四项就可以开始盘点，**不要求用户一次填完所有字段**：

1. 一份简历、自我介绍或现有主页
2. 至少一个社交媒体或作品地址
3. 网站的主要用途
4. 希望访问者做的一个动作

没有正式简历也能开始——从自我介绍 + 社交主页 + 作品链接切入。

**起步回复要轻。** 用户已经列出手上有什么时，第一条回复只请他把这些发过来。不要在还没读过资料时就要求补齐整套字段。

## 渐进式提问

**每次只问当前最重要的一项。** 推荐顺序：

1. 「这个网站最主要帮你获得什么：工作机会、客户、同行认知、内容读者，还是一个长期的个人档案？」
2. 「最希望哪类人访问？」
3. 「看完首页，希望对方做什么？」
4. 「哪三件作品或经历最能证明你？」
5. 「其中你具体负责什么，结果是什么？」
6. 「哪些内容不能公开？」
7. 「以后由谁、以什么频率更新？」

不要重复问已经能从资料里可靠得出的事实。用户主动一次性给一大包资料时，全部接收即可。

## 分批清单（按需取用，不要整份甩给用户）

### 必备
姓名/网名 · 一句话定位（身份 A / B / C）· 联系方式 · 3 条最想被看到的经历或作品

### 身份与经历
工作经历（公司/职位/时间/**做成了什么**，要结果不要职责）· 教育背景 · 技能栈（分类 + 熟练度或年限）· 目标岗位与求职状态 · 是否需要简历 PDF 下载 · 现居城市 · 主业/副业 · 价值观 2–3 条

### 产出与资产
**社交媒体**（主页 URL + 粉丝量/内容量）：公众号、X、小红书、B 站、抖音、即刻、知乎、GitHub、YouTube、播客、Newsletter、LinkedIn、豆瓣、Instagram
**作品**（名称 / 一句话 / 链接 / 截图 / 时间 / 你的角色）：上线产品、开源项目（Star）、设计摄影视频、代表文章 3–5 篇、演讲课程专栏、比赛与 hackathon
**可验证数字**：全网粉丝、产品累计用户、GitHub Star、文章阅读量与篇数、年发布量、服务客户数

### 人味（决定网站好读而不只是好看）
兴趣爱好（要写「玩了多久、到什么程度」）· YearLog（按年一句话）· Now 页（这个月在做/在读/在学）· 服务与合作方式（各自适合谁）· 博客内容从哪来 · 常用工具清单

## 内容实体

把不同来源的资料统一成下面的实体再排版，避免同一件事在多处出现不同版本。

**Profile**：display_name · headline · short_bio · long_bio · location（只到用户授权的精度）· portrait · languages · contact_methods

**Experience**：organization · role · start_date · end_date · responsibilities · achievements · evidence · public_permission

**Project**：title · one_line_summary · problem · audience · role · collaborators · process · outcome · metrics · date · links · media · confidentiality

**Output**（文章/视频/播客/演讲/课程/开源/动态）：title · type · platform · published_at · url · excerpt · topics · engagement（仅在有可靠来源时）· featured

**ProductOrService**：name · audience · problem · promise · status · proof · price_or_contact · url

**Testimonial**：quote · author · relationship · source · **permission**

**SourceRecord**：source_type · source_url_or_file · captured_at · original_text · normalized_entity · confidence · confirmed_by_user

跨平台重复发布的内容**合并为一个实体，保留多个来源链接**。信息冲突时保留两个版本，向用户确认。

## 证据与确认

每条内容归入四类之一，写进站点前心里要清楚它是哪一类：

| 类别 | 来源 | 处理 |
|---|---|---|
| 已证实事实 | 简历、官方项目页、用户明确确认 | 可直接用 |
| 来源摘要 | 从公开内容归纳 | 用，但保留来源链接 |
| AI 建议文案 | 我起草的表达 | 可编辑，**不当作事实来源** |
| 待确认推断 | 从多篇内容推断出的专业方向等 | **必须标记并确认后才上线** |

数字成果优先用可验证口径。无法验证时用具体但不夸张的描述，**不要把关注量、播放量、客户数补成估值**。

## 社交媒体采集

只访问公开页面，按顺序：

1. 读简介、置顶内容、作品链接、可见时间线
2. 识别重复主题、代表内容、发布时间、外部链接
3. 跨平台重复内容合并，保留全部来源
4. 按「与网站目标相关 / 能证明能力 / 仍然有效」筛选，不把所有内容堆到首页
5. **遇到登录墙、验证码、反爬、权限限制立即停止，不尝试绕过**
6. 改请用户提供平台导出文件、文本、链接清单或截图

不使用未经允许的私信、好友可见内容或第三方泄露数据。

| 来源 | 抓法 | 能拿到 |
|---|---|---|
| 简历 docx / pdf / md | Read（docx skill / pdf skill） | 经历、技能、教育 |
| GitHub 主页 | WebFetch `github.com/<user>` | 项目名、Star、语言、简介 |
| 个人博客 / 语雀 | WebFetch | 文章列表、写作主题 |
| X / 小红书 / B 站主页 | claude-in-chrome | 粉丝数、简介、代表内容 |
| 公众号文章 | WebFetch / baoyu-url-to-markdown | 标题、内容、风格 |
| 产品官网 | WebFetch | 一句话介绍、截图素材 |

## 隐私规则

**默认不公开**：详细住址、身份证件信息、私人电话、未授权的私人邮箱、客户内部数据与保密项目、家庭成员与私人关系、简历中仅为招聘流程提供的敏感字段。

发布前**输出一份「将公开的信息清单」**让用户逐项确认。注意：清掉文件的隐藏元数据 ≠ 清掉页面上的文字，两者都要检查。

## 确认输出格式

收完资料后按这个格式回给用户，确认后再进下一步：

```
## 已证实（可直接用）
- 定位：产品经理 / AI 开发者 / 内容创作者
- 经历：3 段（国企 → AI 创业 → 上市公司）
- 数字：全网 10 万粉 / 产品 5 万用户 / Skill 近 200 个（来源：你的简历 + GitHub）

## 待你确认
- 「GitHub 数千 Star」是全部仓库累计还是单个项目？站上要写哪个口径
- 是否公开微信号？现在计划放在首页联系区

## 还缺
- 每款产品的一句话说明（现在只有名字）
- 3 篇代表作链接

## 建议补（会明显提高说服力）
- 产品截图 —— 作品集方向没图会很空
```
